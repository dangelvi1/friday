November 26, 2026. This single package installs directly over the exact delivered v38, v39 or v40 source, both voice families. Twenty-four payload files and six baseline profiles are included. Private Windows configuration/database/credentials and WordPress public drafts are not in this source package.

Existing real PostgreSQL/PGlite/authenticated Express Ads/company/WordPress workflows also passed with controlled provider transports. No real Ads result was submitted to an external model in these tests.
- 126 reported regression entries passed: Google routing, full dashboard chat/files/office workflow, owner sessions, typed commands, shared voice approvals, appointments, office persistence, security, listing receipts/readback, focused commerce, taxonomy verification and calendars. Total in these final runs: 177 reported entries, including Node parent entries. No live provider/phone/financial action was performed.
- The first WordPress browser run exposed a test race: it invoked connect_form while the clicked website tab's async open was still busy, so the intentional busy guard refused the invocation. The fixture now waits for actual panel idle and asserts connect_form success before filling. No WordPress production code was changed for that test fix. Earlier chat/focused-commerce test-only race corrections are retained from v40.
- Both supported frontend voice families passed TypeScript checks. Strict targeted WordPress/marketing backend types and Vite production build passed. configFile:false avoids unavailable private Windows TLS configuration in sanitized cloud source. The existing bundle-size advisory remains. This does not prove the entire private backend or owner's deployment.
- Seventeen actual Linux PowerShell 7 package scenarios passed: install/byte-verified backup/restore with and without optional historical tests across all six v38/v39/v40 profiles, unknown source/main/server/new-file collisions, tampered payload and guarded restore. Test fixture private credential files stayed intact. Windows PowerShell ACL/.cmd execution needs the PC test.
- The bundled unchanged Google credential and WordPress key helpers retain their previously tested seven/three synthetic PowerShell scenarios, respectively; those counts are historical helper evidence, not additional v41 code tests. They preserve existing valid keys/unrelated settings and make verified private .env backups. Source rollback retains private database/config and does not delete provider-native changes.

## Practical limits

No real PC installation, Google OAuth connection, WordPress Application Password, paid advertising, live model session or public page publication was performed here. Tests use controlled provider responses, actual local database/HTTP/browser/SDK flows and synthetic records. The owner must install/build/restart/close old tabs/reconnect, run TEST-ON-PC.md, confirm operational privacy facts, then publish and verify the legal/homepage URLs separately. No developer-token access level, API version availability, public canonical site or Google verification approval is inferred from a passing fixture test.

Consent covers the dedicated conversational Ads tool. Direct dashboard reads remain local to that UI/backend/API path; user-typed messages, manually uploaded Ads files/screenshots and other integrations are separate paths. Previously shared conversation information is not erased by declining. No provider training/retention settings, global interception/DLP, backup expiry, full WordPress media/theme/plugin/building/bulk automation or Ads launching was implemented. WordPress preflight/readback checks remain best effort against concurrent external editors; core REST lacks atomic cross-system compare-and-set. The HTTPS client's DNS resolution has no separate application timeout, although the request/response timeout/cap and public-address pin checks are implemented. Use staging/hosting backups and avoid concurrent editing.
